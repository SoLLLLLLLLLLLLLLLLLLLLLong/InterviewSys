# 智能面试辅导系统面试复习文档

这份文档按“能直接面试表达”的方式整理，重点围绕当前项目真实实现：`Vue 3 + JavaScript + Pinia + Vue Router + Axios + FastAPI + LangGraph + LangChain + Chroma + RAG + MySQL + Redis + ECharts + LangSmith`。

## 一、项目涉及的技术栈

### 1. 前端技术栈

- `Vue 3`：用于实现前端页面和组件化开发。
- `Vite`：前端构建工具，负责本地开发启动和生产构建。
- `JavaScript / ES6+`：实现页面交互、接口调用、异步处理和业务逻辑。
- `Vue Router`：实现首页、工作台、问答模式、模拟面试、历史记录、后台管理等页面路由。
- `Pinia`：统一管理前端状态，例如当前用户、当前模式、会话状态、聊天记录、加载状态、Agent 执行事件。
- `Axios`：处理普通 HTTP 请求，例如登录、注册、文件上传、后台配置、历史记录、报告等。
- `Fetch + ReadableStream + getReader()`：处理流式回复，因为流式接口需要持续读取后端返回的数据块。
- `FormData`：处理简历上传、知识库文档上传等文件上传场景。
- `ECharts`：后台数据看板，展示 Agent 运行状态、耗时趋势、候选人得分趋势、岗位任务分布、题库维度覆盖等。(ECharts 是百度开源的前端图表库，用来画各种统计图。https://echarts.apache.org/zh/index.htmls)
- `CSS / Flex / Grid / 响应式布局`：实现前台工作台、左侧边栏、聊天区、后台 SaaS 风格管理台和移动端适配。
- `Web Speech API`：数字面试官轻量版的语音输入和语音播报。

### 2. 后端技术栈

- `Python`：后端主语言。
- `FastAPI`：提供 HTTP API、文件上传接口、流式响应接口和前端构建产物托管。
- `Pydantic`：定义请求参数结构，例如登录、注册、发送消息、开始面试等请求体。
- `SQLAlchemy 2`：正式模式下操作 MySQL 数据库。(SQLAlchemy 负责把这些 Python 对象和 MySQL 表之间进行映射，开发者不用手写大量 SQL，代码更安全、更易维护。)
- `Alembic`：管理数据库表结构迁移。
- `MySQL`：正式数据模式下保存用户、组织、角色、项目、会话、面试任务、题库、报告、Agent Run 等结构化数据。
- `SQLite / JSON`：本地开发降级模式，保存基础用户数据和工作区快照。
- `Redis`：保存 Agent Run 运行进度、取消标记和短期事件，支持中断恢复和执行过程可视化。(Redis常用于缓存、运行状态、临时数据、消息队列)
- `Uvicorn`：运行 FastAPI 服务。(FastAPI：写业务逻辑（"餐厅后厨"）。
Uvicorn：负责接收 HTTP 请求并把请求交给 FastAPI（"服务员"）)

### 3. AI 应用与 Agent 技术栈

标准回答：

“这个项目是典型的前后端分离式 Web 链路。用户进入页面后，前端先调用 `/api/bootstrap` 初始化当前登录态、工作区和候选人状态。用户操作页面时，比如发送问题、开始面试、上传简历，前端会触发组件事件，再由 `useInterviewApp` 这类 composable 调用封装好的接口。普通接口用 Axios，流式聊天接口用 Fetch 读取流数据。后端 FastAPI 收到请求后，通过 Cookie Session 找到当前用户，调用业务服务、RAG 或 Agent 工作流，最后把最新状态返回给前端。前端更新 Pinia 状态后，Vue 会自动重新渲染页面。”


这是一个面向技术面试准备场景的智能面试辅导 Web 系统，整体是前后端分离的架构。
前端主要用 Vue 3、Pinia、Vue Router、Axios 和 Fetch 实现页面和交互，后端用 FastAPI 提供接口，并结合 LangChain、LangGraph、RAG 和 DeepSeek API 实现智能问答和模拟面试能力。

用户打开系统后，前端会先请求 /api/bootstrap，初始化登录态、用户信息、天气、工作区、会话和页面配置，这样前端先拿到一份完整的初始化数据，再写入 Pinia 状态管理里。

用户登录或注册时，后端校验邮箱和密码，成功后创建 Session，并通过 Cookie 维持登录态。之后前端每次请求，浏览器会自动带上 Cookie，后端就能根据 Cookie 找到当前用户，识别当前用户并做数据隔离。

进入系统后，左侧侧边栏主要是工作区和功能入口，包括项目空间、会话列表、问答模式、模拟面试、历史记录、知识库导入和 LangSmith 调试入口。用户切换会话时，前端调用后端接口，后端返回对应会话的问答历史、面试历史、简历和报告状态，前端写入 Pinia，页面自动更新。

问答模式下，用户输入发送技术问题后，前端先显示用户消息和 AI 占位消息，再用 Fetch 请求流式接口（普通请求一般走 Axios，但问答回复是流式的，所以这里使用 Fetch 请求后端的流式接口。）。后端结合历史上下文、知识库 RAG 和 Tool Calling 生成回答，并持续返回流式数据。前端通过 getReader() 逐段读取内容，实时追加到 AI 气泡里（每拿到一段 token 就追加到 AI 消息气泡里，所以用户能看到模型边生成边显示）。

模拟面试模式下，用户选择岗位，也可以上传简历。后端会根据岗位、简历和后台配置（提示词）初始化面试状态，并通过 LangGraph 多 Agent 和状态机推进流程，比如 Router Agent 判断用户意图，Resume Analyst 分析简历，Interview Agent 生成问题，Evaluation Agent 评估回答质量，状态机决定是追问、提示、切题还是结束。这样可以避免模型一直追问同一个问题，也能让面试更像真实面试官。

系统里还有三种身份：候选人、企业面试官和平台管理员三种角色。候选人使用前台问答和面试；面试官可以在后台管理岗位、题库、候选人和报告；管理员可以管理用户、组织、Prompt、模型配置和 Agent 运行记录。后台还接入了 ECharts，用来展示 Agent 运行状态、耗时趋势、候选人得分趋势和题库覆盖情况。

整体来说，前端负责页面交互和展示、状态管理和流式渲染；后端负责鉴权、业务逻辑、数据存储、RAG 检索和 Agent 编排。后端返回数据后，前端写入 Pinia，Vue 自动更新页面，形成完整的前后端闭环。

## 四、前端实现重点

### 1. 前端整体架构怎么讲？

可以直接记这 5 层：

1. `views`：页面级组件，例如问答页、面试页、历史页、后台页。
2. `components`：可复用组件，例如侧边栏、聊天记录、面试面板、图表卡片。
3. `stores`：Pinia 状态管理，例如 appStore、platformStore。
4. `composables`：业务编排逻辑，例如登录、发送消息、上传文件、流式读取。
5. `api`：统一封装 Axios 和 Fetch 请求。

标准回答：

“前端不是把所有逻辑堆在一个 Vue 文件里，而是按页面、组件、状态、业务逻辑和接口封装分层。页面组件负责展示，子组件负责局部 UI，Pinia 负责全局状态，composable 负责编排业务流程，api 层负责和后端通信。这样代码结构更清晰，也方便后续扩展后台、图表和数字面试官。”

### 2. 为什么用 Pinia？

Pinia 用来保存多个页面都要用到的状态，例如：

- 当前用户 `auth`
- 当前候选人/会话状态 `candidate`
- 当前模式 `mode`
- 工作区 `workspace`
- 聊天输入框 `qaInput / interviewInput`
- 加载状态 `loadingAction`
- 流式生成状态 `typingState`
- Agent 执行事件 `agentEvents`
- 后台图表和配置 `platformStore`

标准回答：

“如果只用组件自己的 state，跨组件传递会很混乱。比如左侧会话切换会影响右侧聊天区、面试区、上传状态和报告区，所以我把这类全局状态放到 Pinia。组件只负责触发事件和展示数据，真正的数据同步放在 store 和 composable 里，状态变化后 Vue 自动重新渲染。”

### 3. 前端如何感知状态变化？

可以直接记这 5 步：

1. 核心状态放在 `ref` 或 Pinia state 里。
2. 派生状态用 `computed` 计算，例如当前历史记录、是否显示欢迎页。
3. 用户操作后触发接口请求。
4. 接口返回后修改响应式状态。
5. Vue 自动追踪依赖并重新渲染组件。

标准回答：

“前端感知状态变化依赖 Vue 的响应式系统。像当前用户、当前模式、聊天记录、输入框内容这些核心状态会放在 Pinia 或 `ref` 里；像当前应该展示哪段历史、是否显示欢迎卡片这种派生结果用 `computed`。
后端返回数据后，前端只要更新这些响应式状态，Vue 就会自动通知依赖它们的组件重新渲染，不需要手动操作 DOM。”

### 4. Axios 和 Fetch 为什么都用？

FormData = 一个专门存放表单数据（尤其是文件）的容器对象，浏览器提供的构造函数（类）

- 通接口用 `Axios + JSON`：请求体通常是普通对象，Axios 自动序列化为 application/json, 写法简洁，适合 JSON 请求、统一错误处理、统一 baseURL。
- 文件上传用 `Axios + FormData`：请求体是 FormData 对象，浏览器会编码为 multipart/form-data
- 流式回复用 `Fetch`：因为 Fetch 原生支持 `ReadableStream`，可以用 `response.body.getReader()` 持续读取后端返回的数据块。

- Axios：负责发送 HTTP 请求（工具）。
- FormData：请求体（Body）的数据容器，用于组织表单字段和文件。
- Fetch：另一种发送 HTTP 请求的方式，原生支持 ReadableStream，适合处理流式响应。

const formData = new FormData();
formData.append("file", file);
axios.post("/upload", formData);

发送的是：multipart/form-data。可以包含：普通文本、图片、PDF、Word、视频、任意二进制文件

标准回答：
按场景分工。登录、注册、后台配置、历史记录这些普通接口走 Axios；聊天和面试这种需要边生成边显示的接口走 Fetch，因为要读取浏览器的 ReadableStream。这样既保留 Axios 的工程封装便利，也能实现真正的流式输出。”

### 5. 流式回复前端怎么实现？

可以直接记这 7 步：

1. 用户发送消息。
2. 前端先插入用户气泡。
3. 再插入一条 assistant 占位气泡。
4. 使用 `fetch` 请求 `/api/qa/chat/stream` 或 `/api/interview/message/stream`。
5. 通过 `response.body.getReader()` 循环读取数据。【字节流】
6. 用 `TextDecoder` 解码文本，再按行解析 JSON 事件。【把字节解码成文本】
7. 收到 `token/chunk` 就追加到 assistant 气泡，收到 `done` 就同步最终状态。

标准回答：
“这个项目现在是真流式，不是前端用定时器模拟。后端会持续返回 NDJSON 事件，例如 `status`、`token`、`done`、`error`。前端用 Fetch 拿到流之后，通过 `getReader().read()` 循环读取，每读到一段就解码并解析事件。如果是 token，就追加到当前 assistant 消息里，所以用户能看到模型边生成边显示。”


第 6 点可以这样理解：
后端流式返回的不是普通字符串，而是一段一段的二进制数据。前端通过 getReader().read() 拿到的 value 本质上是字节流，所以要先用 TextDecoder("utf-8") 把字节解码成文本。
然后后端每次返回的是一行一行的 JSON 事件，比如：
{"type":"token","content":"你好"}
{"type":"token","content":"，我是面试官"}
{"type":"done","candidate":{}}
所以前端会维护一个 buffer，把每次解码出来的文本追加进去，然后按 \n 分割成多行。完整的一行就 JSON.parse() 解析成事件对象；如果最后一行还没接收完整，就先留在 buffer 里，等下一次数据来了再继续拼。

“因为流式接口返回的是字节流，前端不能直接当字符串用，所以我先用 TextDecoder 按 UTF-8 解码成文本。后端约定每一行是一个 JSON 事件，所以前端会用换行符把文本拆成一行一行的数据，再用 JSON.parse 解析出事件类型。比如解析到 token 事件，就把 content 追加到当前 AI 消息里；解析到 done 事件，就同步最终状态。为了防止某一段数据只返回了半行 JSON，我还会用 buffer 暂存未完整的一行，等下一段数据来了再拼接解析。”


### 6. 用户点击停止生成怎么做？

1. 前端保存当前流式请求的 `AbortController`。
2. 用户点击停止时，前端调用后端取消接口写入取消标记。
3. 前端执行 `controller.abort()` 中断当前 fetch。
4. 当前 assistant 消息标记为 `interrupted`，可以继续生成或重试。

标准回答：

“手动停止和断网不一样。手动停止代表用户明确取消，所以前端会先通知后端写取消标记，再 abort 当前 fetch。前端会把当前回复保存为 interrupted 状态，后续可以继续生成或重试。如果是网络意外断开，后台任务可以继续执行，前端再通过 run_id 尝试恢复结果。”

controller.abort() 是 Fetch API 中用于主动取消请求的方法，它和 AbortController 配套使用。很多 AI 聊天（ChatGPT、DeepSeek、Claude）都有一个停止生成按钮，本质上就是用到了它
AbortController：一个"遥控器"，专门控制某个异步任务是否终止
AbortController
├── signal    （交给fetch监听）
└── abort()   （发出终止命令，abort 本质就是关闭当前 HTTP 请求）

const controller = new AbortController();
fetch("/chat", {
    method: "POST",
    signal: controller.signal    //controller.signal→fetch建立了联系。fetch 会一直监听 controller.signal
});

AbortController 是浏览器提供的一个取消异步任务的控制器，主要用于中断 fetch 请求。前端发起流式请求时，会把 controller.signal 传给 fetch，当用户点击"停止生成"时，调用 controller.abort()，浏览器会终止当前 HTTP 请求，fetch 会抛出 AbortError，流式读取循环立即结束。不过在 AI 项目中，通常还需要先通知后端写入取消标记（如 Redis 中的 cancel=true），让后台停止 LLM 推理，再调用 abort() 关闭前端连接，这样既能停止生成，也避免后台继续消耗计算资源。

### 7. 文件上传怎么实现？

1. 用户选择文件。
2. 前端从 input 拿到 `File` 对象。
3. 创建 `FormData`，把文件 append 进去。
4. Axios 请求上传接口，例如 `/api/resume/upload` 或 `/api/knowledge/import`。
5. 后端解析文件，保存文件，提取文本或导入知识库。

“文件上传不能像普通 JSON 一样传，因为文件是二进制数据。前端使用浏览器提供的 FormData，把文件放到 multipart/form-data 请求里。后端 FastAPI 用 UploadFile 接收，再根据文件类型做解析、保存和后续处理。”

### 8. ECharts 在项目里做什么？

ECharts 是前端图表库，用于把后台统计数据可视化。本项目里封装了 `ChartCard` 组件，用于展示：

- Agent 运行状态分布
- Agent 延迟趋势
- 候选人得分趋势
- 岗位任务分布
- 岗位模板分布
- 题库维度覆盖

标准回答：

“后台如果只是表格，会比较像 Demo。我引入 ECharts 做管理台数据看板，把 Agent 运行、面试业务和题库配置变成可视化图表。前端从 `/api/platform/charts` 获取数据，再通过 ChartCard 统一渲染柱状图、折线图或饼图。”

## 五、后端实现重点

### 1. FastAPI 在项目里负责什么？
FastAPI 是项目的后端接口层，负责接收前端请求、校验参数、完成用户认证，并提供问答、模拟面试、文件上传、会话管理、历史记录、Agent 运行控制等接口。同时，它还支持流式响应和静态页面托管。本身并不直接负责大模型推理，而是将请求转发给 LangChain、LangGraph、RAG 等业务服务，最后将结果以 JSON 或流式数据返回给前端。

### 2. 登录鉴权怎么实现？
1. 用户输入邮箱和密码。
2. 前端调用登录接口。
3. 后端校验用户表中的密码。
4. 校验成功后生成 session token。
5. 后端通过 `Set-Cookie` 写入浏览器 Cookie。
6. 后续请求浏览器自动携带 Cookie，后端根据 Cookie 找当前用户。

“当前项目是 Cookie Session 鉴权，不是 localStorage 存 token。登录成功后，后端生成 session token 并写入 HttpOnly Cookie。后续请求时浏览器会自动携带 Cookie，后端再根据 session token 查到当前用户。这样前端不用手动在请求头里拼 Authorization，也比 localStorage 存敏感 token 更安全一些。”

### 3. 数据存在哪里？

当前项目分两种模式：
- 开发降级模式：SQLite + JSON + 本地文件。
- 正式数据模式：MySQL + Redis + Chroma + 本地上传文件。

正式模式下：
- MySQL：用户、组织、角色、项目、会话、面试任务、题库、报告、Agent Run 元数据。
- Redis：Agent Run 临时事件、取消标记、运行进度。
- Chroma：知识库文档向量。
- 本地文件夹：上传文档、上传简历、导出的报告文件。

“MySQL 保存结构化业务数据，Redis 保存短期运行状态，Chroma 保存向量索引，本地文件夹保存上传原文件和报告文件。它们分工不同：MySQL 适合查用户、会话、任务；Redis 适合快速保存运行进度；Chroma 适合相似度检索；文件系统适合保存文档和报告。”

### 4. MySQL 和 Chroma 有什么区别？
MySQL 和 Chroma 解决的问题不一样

- MySQL 是关系型数据库，适合存用户、订单、会话、报告这类结构化业务数据，适合 SQL 查询和事务管理。
- Chroma 是向量数据库，保存的是文档切片的 embedding 向量，主要用于 RAG 检索， 适合存文本向量，用于语义相似度检索。
- MySQL 查的是“字段匹配”，Chroma 查的是“语义相似”。

### 5. Redis 在项目里做什么？
“Redis 不是用来替代 MySQL 的，而是保存短期、高频、临时状态。比如一次多 Agent 面试执行过程中，会产生节点开始、工具调用、检索完成、token 输出这些事件，这些事件适合放到 Redis 里，前端断线后也可以根据 run_id 查询运行结果。”

Redis 主要用于：
- 保存 Agent Run 执行进度：比如当前执行到 Router、Evaluation 还是 Report 节点，后台可以展示 Agent 运行时间线
- 保存流式事件临时队列：Agent 每产生一个事件，就追加到 Redis。前端流式读取时，可以把这些事件展示出来
- 保存取消标记：用户点击“停止生成”时，前端调用取消接口，后端把这个 run 标记为 cancelled。Agent 执行过程中可以检查这个标记，决定是否停止继续生成
- 支持断线后通过 `run_id` 恢复：如果用户刷新页面或网络断开，前端当前 fetch 断了，但后端任务可能还在跑。只要 Redis 里还保存着 run_id 对应的状态，前端重新进入页面后就可以根据 run_id 查询运行结果，把最终回复恢复回来。

Redis 主要不是存长期业务数据，而是存“一次 Agent 运行过程中的临时状态”。比如用户回答一道面试题后，后端会创建一个 run_id，这次回答处理过程就对应一个 Agent Run。后续 LangGraph / Agent 每执行一步，都会把事件写到这个 run 下面。
- 一次面试回答大概是这样：用户提交回答 → 后端创建 run_id → Router Agent 开始 → Evaluation Agent 开始 → Tool 被调用 → RAG 检索完成 → Interview Agent 生成 token → Agent Run 完成 → 前端根据 run_id 接收或恢复结果

Redis 里适合保存类似这种结构：
{
  "run_id": "abc123",
  "status": "running",
  "current_node": "evaluation_agent",
  "events": [
    {"type": "run_started", "content": "面试工作流已启动"},
    {"type": "node_started", "node": "router_agent"},
    {"type": "tool_called", "tool": "knowledge_search"},
    {"type": "token", "content": "我们换一个方向..."}
  ],
  "cancelled": false,
  "result": null
}
后端流式接口会一边执行 Agent，一边读取这些事件，再通过 HTTP 流式响应返回给前端。前端收到事件后，就能显示“正在分析简历 / 正在评估回答 / 正在生成问题”等状态，也能把 token 追加到聊天气泡里。

Redis 在我这个项目里主要存 Agent 执行过程的短期状态。每次用户发送面试回答，后端会创建一个 run_id，然后把这次 Agent 工作流执行过程中的节点事件、工具调用事件、token 输出、取消标记和最终结果都挂在这个 run_id 下面。前端流式展示时可以实时读取这些事件；如果用户断网或刷新页面，也可以用 run_id 去恢复这次运行结果。MySQL 负责存长期业务数据，Redis 负责存短期运行状态，两者职责不一样。”

## 六、RAG 与知识库实现

### 1. RAG 完整链路是什么？
“RAG 的作用是让模型回答时能结合本地知识库，而不是只靠模型自身参数。上传文档后，系统会解析、切分、向量化并存入 Chroma。用户提问时，系统先检索相关片段，再把片段作为上下文拼进 Prompt，让模型基于资料回答。”

1. 用户上传知识库文档。
2. 后端保存文件。
3. 文档解析成文本。
4. 文本切分成 chunks。
5. 调用 embedding 模型生成向量。
6. 存入 Chroma。
7. 用户提问时，先召回相关 chunks。
8. 把检索结果作为上下文交给大模型生成回答。

### 2. BM25、向量召回、Rerank 分别是什么？
“单独向量召回有时会漏掉关键词非常重要的问题，单独 BM25 又不理解语义。所以我设计上保留混合检索：向量召回负责语义，BM25 负责关键词，RRF 做融合，Rerank 做最终排序。这样能兼顾召回率和准确率。”

- 向量召回：根据语义相似度找文档，适合语义表达不同但意思接近的问题。
- BM25：根据关键词匹配找文档，适合专有名词、技术名词、精确关键词。
- RRF：融合多路召回结果。
- Rerank：对候选结果重新排序，让最相关的内容排前面。

### 3. 如果知识库没有答案怎么办？
“如果检索不到足够相关的资料，系统不会强行说知识库里有答案，而是会降级到模型通用能力回答，并提示资料可能不足。更正式的做法是通过 Evidence Judge 判断证据是否足够，不足时补查一次，仍不足就明确说明依据有限，避免幻觉。”

## 七、Agent 与模拟面试实现

### 1. 这个项目为什么算 Agent 应用？
它不只是简单调用一次大模型（不是单纯聊天机器人），而是围绕面试任务做了工作流编排。系统会分析简历、规划面试维度、生成问题、评估回答、决定追问或切题、最后生成报告。每一步都有状态和节点记录，所以更接近 Agent Workflow。具备：

- 工具调用：模型可以决定查知识库、查天气、保存报告等。
- 多 Agent 分工：Router、Resume Analyst、Interview、Evaluation、Report 等角色。
- 状态管理：保存当前题目、回答质量、追问次数、面试进度。
- 工作流编排：LangGraph 控制节点顺序。
- 可观测性：LangSmith 和后台 Agent Run 记录。

### 2. 多 Agent 是怎么分工的？

可以直接记：

- `Router Agent`：判断用户意图，是回答问题、要求提示，还是结束面试。
- `Resume Analyst Agent`：分析简历，提取项目、技术栈、亮点和风险点。
- `Interview Planner`：根据岗位、简历和后台模板生成面试计划。
- `Interview Agent`：像面试官一样自然提问。
- `Evaluation Agent`：评估用户回答质量，给出分数、薄弱点和追问建议。
- `Evidence Judge`：判断检索证据是否相关、是否足够。
- `Report Agent`：生成结构化面试报告。

标准回答：

“我把一个复杂面试任务拆成多个职责单一的 Agent，而不是让一个 Prompt 做所有事情。Router 负责分流，Resume Analyst 负责简历理解，Interview Agent 负责提问，Evaluation Agent 负责评分，Report Agent 负责总结。这样每个节点更容易调试，也方便在 LangSmith 里观察具体哪一步出问题。”

### 3. LangGraph 和状态机有什么区别？

可以直接记：

- LangGraph 管“有哪些节点、节点怎么流转”。
- 状态机管“面试业务规则”，例如最多问几题、追问几次、什么时候切题、什么时候结束。

标准回答：

“LangGraph 更像多 Agent 工作流编排框架，负责 Router、Evaluation、Interview、Report 这些节点怎么串起来；状态机更像业务规则控制器，负责限制追问次数、题目数量和结束条件。两者配合后，模型负责生成和判断，状态机保证流程可控。”

### 4. 面试状态机怎么避免一直追问一个问题？

可以直接记：

- 记录当前问题。
- 记录追问次数。
- 记录回答得分。
- 如果连续回答较弱，可以先给提示。
- 如果追问达到上限，就切换到下一个能力维度。
- 面试题数达到上限后结束。

标准回答：

“之前模型容易一直围绕一个点追问，所以我加了状态机。它会记录当前问题、追问次数、回答质量和已问知识点。如果回答不好，可以追问或提示，但追问有上限；达到上限后必须切换到下一个维度。这样面试更像真实面试官，不会卡死在一个问题上。”

### 5. 后台岗位题库如何驱动前台面试？

可以直接记这 5 步：

1. 面试官在后台新增岗位模板、能力维度和题库。
2. 前台进入模拟面试或开始面试前请求 `/api/roles` 刷新岗位列表。
3. 后端开始面试时读取对应岗位模板 profile。
4. 后端把维度计划、题量、题库参考写入 `interview_state`。
5. Interview Agent 生成问题时参考题库方向，但不机械照抄。

标准回答：

“岗位不是前端写死的。后台新增岗位模板后，前台会刷新岗位列表。开始面试时，后端读取该岗位的模板和题库，把能力维度和题库参考注入面试状态和 Prompt。模型提问时会参考这些配置，所以后台配置能真实影响前台面试流程。”

### 6. Tool Calling 是怎么用的？

Tool Calling 的核心是：模型不是只生成文本，而是可以选择调用工具。
“问答模式下，我把知识库检索、天气查询、报告保存等能力封装成工具，交给 Agent 判断是否调用。比如用户问技术知识点，Agent 更可能调用知识库；用户问天气，就调用天气工具。这样比固定 if else 更灵活，也更符合 Agent 应用的设计。”

本项目可讲的工具包括：

- `knowledge_search`：查询知识库。
- `weather_search`：查询天气。
- `resume_lookup`：读取简历上下文。
- `save_report`：保存报告。
- `question_search`：查询题库或面试问题。


### 7. LangSmith 起什么作用？

LangSmith 用于调试和可观测：

- 看每次模型调用的输入输出。
- 看 Prompt 是否符合预期。
- 看 Tool Calling 是否调用了正确工具。
- 看每个节点耗时和错误。
- 复盘失败案例。

标准回答：

“LangSmith 对 Agent 项目很重要，因为 Agent 链路不是一个简单函数，而是多个模型调用、工具调用和状态流转。接入 LangSmith 后，可以看到一次请求经过了哪些节点、Prompt 是什么、工具有没有调对、哪里耗时最多、哪里报错。它主要用于调试、评测和优化。”

## 八、流式、中断和恢复

### 1. 后端流式响应怎么实现？

可以直接记：

- FastAPI 返回 `StreamingResponse`。
- 后端按行返回 JSON 事件。
- 每行事件包含类型，例如 `run_started`、`node_started`、`tool_called`、`token`、`done`、`run_error`。
- 前端逐行解析并更新页面。

标准回答：

“后端不是等模型完整生成完再返回，而是用 FastAPI 的 StreamingResponse 持续 yield 数据。每个事件是一行 JSON，前端读到 token 就更新气泡，读到 node_started 就更新 Agent 执行面板，读到 done 就同步最终 candidate 状态。”

### 2. 用户断网、刷新、超时怎么办？

可以直接记：

- 手动停止：写取消标记 + abort fetch + 标记 interrupted。
- 网络断开：后端任务可以继续跑。
- 页面刷新：前端重新 bootstrap，如果发现 pending run_id，就尝试恢复。
- 模型失败：返回错误事件，前端显示可重试。

标准回答：

“我把手动停止和意外断线区分开。手动停止表示用户不要这个结果了，所以前端通知后端取消并中断请求。断网或刷新则不一定要取消后台任务，后端会保留 run_id 和运行事件，前端恢复后可以用 run_id 查询最终结果。这样能避免用户因为网络波动丢掉一整轮模型输出。”

## 九、后台管理与权限

### 1. 后台分哪些角色？

- 候选人：使用前台问答、模拟面试、查看自己的历史记录和报告。
- 企业面试官：管理岗位模板、题库、候选人、面试任务和报告。
- 平台管理员：管理用户、组织、角色、Prompt 版本、模型配置、Agent Run 和评测指标。

标准回答：

“我把后台拆成企业面试官后台和平台管理员后台。面试官关注业务闭环，例如岗位、题库、候选人和报告；管理员关注平台治理，例如用户权限、组织、Prompt、模型配置和 Agent 运行观测。这样角色边界更清晰，也更像真实 SaaS 系统。”

### 2. RBAC 怎么理解？

RBAC 是基于角色的权限控制。

可以直接记：

- 前端根据用户角色显示不同入口。
- 后端根据用户角色校验接口权限。
- 前端隐藏按钮只是体验优化，后端权限校验才是安全边界。

标准回答：

“RBAC 就是不同角色能访问不同资源。比如候选人不能进入管理员后台，面试官只能看自己组织的数据，管理员能看全平台数据。前端会根据角色控制页面入口，但真正安全要靠后端接口校验，不能只靠隐藏按钮。”

## 十、数字面试官实现

### 1. 数字面试官做了什么？

- 显示面试官形象。
- 展示当前 Agent 状态，例如正在分析简历、正在生成问题、正在评分。
- 支持语音播报面试官问题。
- 支持用户语音输入或文字输入。
- Live2D 可选，如果画面不可用，使用 CSS 兜底形象。

标准回答：

“数字面试官是前端交互增强，不改变后端面试主流程。文字输入和语音输入最终都会变成文本，调用同一个面试接口。AI 回复后，数字面试官用浏览器语音播报，同时普通 AI 气泡可以隐藏，让用户感觉是在和面试官交流。”

### 2. 如果数字人没有画面但有声音，可能是什么原因？

可能原因：

- Live2D 服务没有启动。
- `VITE_LIVE2D_URL` 没配置或地址不通。
- 浏览器跨域或资源加载失败。
- 模型资源路径不对。

标准回答：

“语音播报用的是浏览器 SpeechSynthesis，和 Live2D 画面不是同一套机制。所以即使 Live2D iframe 没加载成功，声音也可能正常。项目里做了 CSS 兜底形象，避免数字人服务不可用时页面空白。”

## 十一、常见基础知识点

### 1. Vue 3 和 Vue 2 区别

- Vue 3 支持 Composition API，更适合复杂逻辑拆分复用。
- Vue 3 响应式底层使用 Proxy。
- Vue 3 TypeScript 支持更好。
- Vue 3 性能和 Tree-shaking 更好。
- 当前项目主要使用 Vue 3 的 `<script setup>` 和 composable 思路。

### 2. ref 和 reactive 区别

- `ref` 适合基本类型，也可以放对象，访问值用 `.value`。
- `reactive` 适合对象或数组，直接访问属性。
- 项目里全局状态更多交给 Pinia，组件内部小状态可以用 `ref`。

### 3. computed 和 watch 区别

- `computed` 用于根据已有状态计算新结果，有缓存。
- `watch` 用于监听状态变化并执行副作用，例如状态变化后关闭弹窗、触发请求。

### 4. ES6+ 项目里常见用法

- `const / let`
- 箭头函数
- 模板字符串
- 解构赋值
- 展开运算符 `...`
- Promise / async / await
- import / export 模块化
- 可选链 `?.`
- 空值合并 `??`

### 5. HTTP、Axios、Fetch、SSE、WebSocket 区别

- HTTP：请求响应协议。
- Axios/Fetch：浏览器发 HTTP 请求的方式。
- SSE：服务端持续向浏览器推送文本事件。
- WebSocket：浏览器和服务器建立双向长连接。
- 当前项目普通接口是 HTTP + Axios，流式聊天是 HTTP 流式响应 + Fetch，不是 WebSocket。

### 6. Flex 布局常见知识点

- `display: flex`
- `flex-direction`
- `justify-content`
- `align-items`
- `gap`
- `flex: 1`

## 十四、Bootstrap 初始化接口

### 1. 这个项目里有 Bootstrap 吗？

有，但这里说的 `bootstrap` 主要不是 Bootstrap CSS/UI 框架，而是项目里的初始化接口 `/api/bootstrap`。

Bootstrap 在这个项目里的含义是“页面启动时一次性拉取前端运行所需的基础数据”，也可以理解成“首屏初始化数据包”。

### 2. `/api/bootstrap` 主要返回什么？

可以直接记这 7 类：

1. 当前登录状态和用户信息：`auth`
2. 当前候选人工作状态：`candidate`
3. 当前项目和会话列表：`workspace`
4. 历史面试记录：`history_records`
5. 天气信息：`weather`
6. LangSmith 调试配置：`langsmith`
7. 页面基础配置：`meta`，例如岗位选项、问答模式文案、模拟面试文案

标准回答：

“这个项目里有一个 `/api/bootstrap` 初始化接口。用户打开页面后，前端不会一个一个接口分散请求用户信息、会话列表、天气、候选人状态和页面配置，而是先请求 bootstrap。后端一次性返回当前登录态、工作区、候选人状态、天气、LangSmith 配置和页面 meta。前端拿到后写入 Pinia，页面就能完成首屏初始化。”

### 3. 为什么要设计 `/api/bootstrap`？

可以直接记这 5 点：

1. 减少首屏请求数量。
2. 避免页面多个模块各自请求导致状态不一致。
3. 让前端启动流程更清晰。
4. 刷新页面后可以恢复用户当前工作状态。
5. 方便后端统一决定当前用户能看到什么数据。

标准回答：

“我设计 bootstrap 的主要原因是首屏需要的数据比较多，如果让每个组件各自请求，会出现请求分散、加载顺序混乱、状态难同步的问题。用 bootstrap 后，前端启动时只需要先拿一份完整状态包，再统一写入 Pinia。这样刷新页面、切换用户、恢复会话都更稳定。”

### 4. 前端怎么使用 `/api/bootstrap`？

可以直接记这 5 步：

1. `App.vue` 挂载时调用 `useInterviewApp().bootstrap()`。
2. `bootstrap()` 使用 `apiGet("/api/bootstrap")` 请求后端。
3. 后端返回完整初始化数据。
4. 前端调用 `appStore.applyBootstrapPayload(data)` 写入 Pinia。
5. 页面根据 Pinia 状态渲染登录页、首页、工作台或后台。

标准回答：

“前端在应用启动时调用 bootstrap 方法，内部请求 `/api/bootstrap`。请求成功后，不是在页面里零散赋值，而是统一调用 `applyBootstrapPayload` 把 auth、candidate、workspace、weather、meta 这些数据写入 Pinia。之后页面根据这些响应式状态判断显示登录页还是工作台。”

### 5. `/api/bootstrap` 和前端路由是什么关系？

可以这样理解：

- `bootstrap` 负责回答“当前用户是谁、有哪些数据”。
- `Vue Router` 负责回答“当前 URL 应该显示哪个页面”。
- `Pinia mode` 负责回答“工作台里当前是问答、面试还是历史记录”。

标准回答：

“bootstrap 不负责页面跳转，它只负责拿初始化数据。页面跳转由 Vue Router 控制，工作台内部模式由 Pinia 里的 mode 控制。也就是说，bootstrap 是数据入口，Router 是页面入口，Pinia 是状态中心。”

### 6. Bootstrap 和普通接口有什么区别？

普通接口通常只负责一个动作，例如登录、发送消息、上传文件、创建会话。Bootstrap 是系统启动时的聚合接口，它不代表一个业务动作，而是为了让前端恢复完整运行环境。

可以直接记：

- 普通接口：处理具体动作。
- Bootstrap：恢复整体状态。
- 普通接口返回局部结果。
- Bootstrap 返回首屏所需的整体数据包。

## 十五、通用设计思路和为什么这样设计

### 1. 为什么要做前后端分层？

可以直接记：

1. 前端负责页面展示和用户交互。
2. 后端负责业务规则、数据安全和模型调用。
3. 数据库负责持久化。
4. Agent/RAG 负责智能能力。

标准回答：

“前后端分层的好处是职责清晰。前端不直接操作数据库，也不暴露 API Key；后端统一处理鉴权、业务逻辑和模型调用；数据库只负责数据存储。这样安全性、可维护性和扩展性都会更好。”

### 2. 为什么普通请求用 Axios，流式请求用 Fetch？

设计原因：

- Axios 更适合普通 JSON 接口，封装方便。
- Fetch 更适合读取浏览器原生 `ReadableStream`。
- 流式回复需要边读边渲染，所以保留 Fetch。

面试表达：

“我不是随便混用 Axios 和 Fetch，而是按能力选择。普通接口追求封装和错误处理，所以用 Axios；流式接口需要持续读数据流，所以用 Fetch + getReader。这是根据场景做的技术取舍。”

### 3. 为什么要用 Pinia，而不是所有状态都放组件里？

设计原因：

- 聊天记录、用户信息、当前会话会被多个组件使用。
- 左侧边栏、主聊天区、历史记录、后台入口都依赖同一份状态。
- 用 Pinia 可以避免多层 props 传递。
- 状态集中后更容易调试。

面试表达：

“如果状态只放在组件内部，切换会话或模式时会有很多跨组件同步问题。Pinia 相当于前端统一状态中心，组件只关心展示和事件，业务状态统一管理，后续扩展后台和图表也更方便。”

### 4. 为什么要有 composable？

Composable 是 Vue 3 里复用逻辑的一种方式。项目里 `useInterviewApp` 就是把登录、发送消息、上传文件、流式读取、会话管理这些业务流程集中起来。

设计原因：

- 避免组件文件过大。
- 把 UI 和业务逻辑分开。
- 多个页面可以复用同一套逻辑。
- 更方便测试和排查问题。

面试表达：

“我把复杂业务流程放到 composable，而不是写死在组件里。组件负责展示，composable 负责业务编排，比如发送消息要先乐观更新，再请求流式接口，再处理中断和错误。这样页面更干净，逻辑也更容易复用。”

### 5. 为什么后端要做权限校验，前端隐藏按钮不够吗？

前端隐藏按钮只是用户体验，不是安全边界。用户可以绕过页面，直接用 Postman 或浏览器请求接口。

正确设计：

- 前端根据角色显示入口。
- 后端根据 Cookie 找用户。
- 后端检查用户角色和组织权限。
- 没权限直接返回 403。

面试表达：

“权限不能只靠前端控制。前端隐藏按钮只是减少误操作，真正安全要靠后端 RBAC 校验。比如候选人即使手动请求管理员接口，后端也要拒绝。”

### 6. 为什么要做状态机，而不是完全交给大模型？

设计原因：

- 大模型容易一直追问同一个问题。
- 大模型不一定知道什么时候结束。
- 面试需要题数、追问次数、切题条件这些确定规则。
- 状态机可以保证流程可控。

面试表达：

“大模型擅长生成自然语言，但不适合完全控制业务流程。所以我把面试流程规则交给状态机，例如最多问 8-10 题、追问不超过上限、回答太弱先提示、达到条件就切题或结束。这样既保留模型自然提问能力，也保证流程稳定。”

### 7. 为什么要做 Agent Run 可视化？

设计原因：

- Agent 链路比普通接口复杂。
- 一次请求可能经过多个节点和工具。
- 出错时需要知道是检索失败、模型失败、评分失败还是报告失败。
- 面试展示时也能体现系统不是简单聊天机器人。

面试表达：

“Agent 系统如果不可观测，调试会很困难。我把节点事件、工具调用、检索结果、耗时和错误记录下来，并在后台展示。这样可以定位问题，也能分析系统质量，比如哪个节点慢、哪个工具经常失败。”

### 8. 为什么要做中断恢复？

设计原因：

- 大模型回复可能很慢。
- 用户可能刷新页面或网络断开。
- 如果没有恢复机制，一轮长回答就丢失了。
- run_id 可以把前端请求和后端执行任务关联起来。

面试表达：

“中断恢复对 Agent 应用很重要，因为一次任务可能比较长。项目里通过 run_id 记录本轮执行，前端断线后可以重新查询运行结果。这样比简单报错更可靠，也更接近真实产品设计。”

### 9. 为什么要做后台岗位题库配置？

设计原因：

- 如果岗位和题库写死在前端，不方便业务人员维护。
- 后台配置后，面试官可以管理不同岗位和能力维度。
- 前台面试可以读取后台配置，提问更贴近岗位。

面试表达：

“后台岗位题库配置的意义是把系统从个人 Demo 变成可运营产品。面试官可以维护岗位模板、题库和评分维度，前台开始面试时读取这些配置，让 Agent 按业务配置推进，而不是所有内容都写死在代码里。”

### 10. 为什么要做 ECharts 看板？

设计原因：

- 后台不能只有表格。
- 图表更适合展示趋势和分布。
- Agent 运行状态、候选人得分、岗位任务、题库覆盖都适合可视化。

面试表达：

“ECharts 看板主要是增强后台产品感和可观测性。管理员可以看 Agent 运行状态和耗时，面试官可以看候选人得分趋势和岗位分布。这样后台不只是 CRUD，而是能支撑运营和分析。”

设计原因：

## 十六、今日面试新增高频题

这一节是根据今天真实面试被问到的问题补充的，优先用于前端实习面试快速背诵。

### 1. v-for 和 v-if 能不能同时使用？

可以同时写在同一个元素上，但一般不推荐。

原因是：

- `v-for` 和 `v-if` 同时使用时，可读性比较差。
- Vue 里它们有优先级问题，不同版本行为也容易让人混淆。
- 如果在循环里再判断，会让每一项都执行条件判断，性能和维护性都不太好。

更推荐两种写法：

1. 先用 `computed` 过滤数据，再用 `v-for` 渲染。
2. 把 `v-if` 放到外层容器，`v-for` 放到内层列表。

示例：

```vue
<template>
  <ul v-if="visibleUsers.length">
    <li v-for="user in visibleUsers" :key="user.id">
      {{ user.name }}
    </li>
  </ul>
</template>

<script setup>
import { computed } from 'vue'

const visibleUsers = computed(() => {
  return users.value.filter(user => user.active)
})
</script>
```

面试表达：

“可以同时使用，但实际开发里不太建议放在同一个标签上。更好的做法是先用 computed 把要展示的数据过滤出来，再用 v-for 渲染，或者把 v-if 放在外层容器上。这样代码更清楚，也避免每次循环都做条件判断。”

### 2. JavaScript 处理对象有哪些常见操作？

可以直接记这 8 类：

1. 读取属性：`obj.name`、`obj['name']`。
2. 新增属性：`obj.age = 18`。
3. 修改属性：`obj.name = 'Tom'`。
4. 删除属性：`delete obj.name`。
5. 遍历对象：`for...in`、`Object.keys()`、`Object.values()`、`Object.entries()`。
6. 合并对象：`Object.assign()`、展开运算符 `{ ...obj }`。
7. 判断属性是否存在：`'name' in obj`、`obj.hasOwnProperty('name')`。
8. 深浅拷贝：浅拷贝用展开运算符，深拷贝可用 `structuredClone()` 或工具库。

示例：

```js
const user = { name: 'Tom', age: 18 }

console.log(user.name)
user.age = 20

const newUser = { ...user, role: 'admin' }

Object.entries(newUser).forEach(([key, value]) => {
  console.log(key, value)
})
```

### 7. async / await 和 Promise 是什么？什么时候用？

`Promise` 是 JavaScript 处理异步操作的一种对象，表示一个未来才会完成的结果。  
`async / await` 是基于 Promise 的语法糖，让异步代码写起来更像同步代码。

- 请求后端接口。
- 上传文件。
- 等待模型返回结果。
- 读取流式响应。
- 多个异步任务按顺序执行。

示例：

```js
async function loadUser() {
  try {
    const response = await axios.get('/api/me')
    user.value = response.data
  } catch (error) {
    console.error('获取用户失败', error)
  }
}
```

面试表达：

补充一句：

“async 函数本身返回的也是 Promise，所以它不是替代 Promise，而是让 Promise 写法更清晰。”

### 10. 了解 for 循环里的 key 和 value 吗？

这个问题可能有两种意思：一种是 JavaScript 遍历对象的 key/value，另一种是 Vue 列表渲染里的 `:key`。

#### JavaScript 里的 key 和 value

对象里：

```js
const user = { name: 'Tom', age: 18 }

for (const key in user) {
  const value = user[key]
  console.log(key, value)
}

Object.entries(user).forEach(([key, value]) => {
  console.log(key, value)
})
```

数组里：

```js
const list = ['a', 'b', 'c']

list.forEach((value, index) => {
  console.log(index, value)
})
```

#### Vue v-for 里的 key

Vue 里的 `:key` 是给每个列表项一个稳定唯一标识，帮助 Vue 判断哪些节点需要复用、移动或重新渲染。

示例：

```vue
<li v-for="item in list" :key="item.id">
  {{ item.name }}
</li>
```

面试表达：

“如果是 JS 对象遍历，key 是属性名，value 是属性值；如果是数组遍历，index 是下标，value 是当前元素。如果是 Vue 的 v-for，:key 是列表项的唯一标识，主要帮助 Vue 做 diff，提高渲染准确性和性能。实际开发里最好用稳定 id，不建议随便用 index 当 key。”

### 11. 为什么 v-for 里不建议用 index 当 key？

因为 index 会随着数组增删排序发生变化，可能导致 Vue 复用错误的 DOM 节点，特别是列表项里有输入框、选中状态或组件内部状态时更容易出问题。

面试表达：

“如果列表只是纯展示，用 index 问题不大；但如果列表会新增、删除、排序，最好用后端返回的 id 作为 key。因为 id 是稳定的，Vue 能准确判断每一项对应哪个 DOM 节点。”

### 12. 前端常见尺寸单位有哪些？px、em、rem、vw、vh、rpx 分别是什么？

可以直接记这 6 类：

1. `px`：像素，固定单位，最常见。
2. `em`：相对于当前元素字体大小。
3. `rem`：相对于根元素 `html` 的字体大小。
4. `vw`：视口宽度的百分比，`1vw` 等于屏幕宽度的 1%。
5. `vh`：视口高度的百分比，`1vh` 等于屏幕高度的 1%。
6. `rpx`：微信小程序常用响应式单位，会根据屏幕宽度自动换算。

#### px

`px` 是固定像素单位，比如：

```css
.button {
  width: 120px;
  height: 40px;
}
```

优点是直观，缺点是不同屏幕上适配性没那么强。

#### em

`em` 相对于当前元素或父元素的字体大小。比如父元素字体是 `16px`，那么 `2em` 就是 `32px`。

```css
.title {
  font-size: 16px;
  margin-top: 2em;
}
```

#### rem

`rem` 相对于根元素 `html` 的字体大小。比如 `html` 是 `16px`，那么 `1rem = 16px`。

```css
html {
  font-size: 16px;
}

.card {
  padding: 1rem;
}
```

`rem` 常用于做整体响应式布局，因为统一改根字体大小，页面很多尺寸都可以一起变化。

#### vw / vh

`vw` 和 `vh` 是根据浏览器视口大小计算的。

```css
.page {
  width: 100vw;
  min-height: 100vh;
}
```

`100vw` 表示整个屏幕宽度，`100vh` 表示整个屏幕高度，适合做全屏页面、弹窗、背景区域。

#### rpx

`rpx` 是微信小程序里的响应式像素单位。微信小程序规定屏幕宽度通常按 `750rpx` 来换算，不同设备会自动适配。

例如：

```css
.container {
  width: 750rpx;
  padding: 32rpx;
}
```

可以简单理解为：

- 在小程序里，`rpx` 更适合做自适应布局。
- 设计稿如果是 750 宽，小程序里写 `750rpx` 就相当于占满屏幕宽度。
- `px` 是固定像素，`rpx` 会根据屏幕宽度自动缩放。

面试表达：

“Web 里常见单位有 px、em、rem、vw、vh。px 是固定像素，rem 相对于根元素字体大小，vw/vh 相对于屏幕宽高。小程序里常用 rpx，它会根据设备宽度自动换算，适合做移动端自适应。比如微信小程序通常把屏幕宽度看成 750rpx，如果设计稿也是 750 宽，用 rpx 还原会比较方便。”

### 13. px 和 rpx 有什么区别？

`px` 是固定像素单位，`rpx` 是微信小程序里的响应式单位。

可以直接记：

1. `px` 不会自动根据屏幕宽度缩放。
2. `rpx` 会根据屏幕宽度自动换算。
3. Web 页面常用 `px/rem/vw/vh`。
4. 微信小程序常用 `rpx`。
5. 移动端适配时，`rpx` 比固定 `px` 更方便。

面试表达：

“px 是固定像素，写多少就是多少；rpx 是小程序的响应式单位，会根据设备宽度自动换算。比如同样写 375rpx，在不同手机上会按屏幕比例适配，所以小程序里做布局经常用 rpx。”

### 14. 路由守卫有了解吗？没有权限的用户怎么处理？

路由守卫就是在页面跳转前或跳转后执行的一段逻辑，常用于登录校验、权限判断、页面标题设置等。

Vue Router 里常见的是全局前置守卫：

```js
router.beforeEach((to, from, next) => {
  const isLogin = authStore.isLogin
  const role = authStore.user?.role

  if (to.meta.requiresAuth && !isLogin) {
    next('/login')
    return
  }

  if (to.meta.roles && !to.meta.roles.includes(role)) {
    next('/403')
    return
  }

  next()
})
```

可以直接记这 4 步：

1. 路由配置里给需要权限的页面加 `meta`。
2. 跳转前在 `beforeEach` 里判断是否登录。
3. 再判断用户角色是否符合页面要求。
4. 不符合就跳转登录页、403 无权限页或首页。

面试表达：

“路由守卫主要用于页面访问控制。比如后台管理页只有 admin 或 interviewer 能进，我会在路由 meta 里配置需要的角色，然后在 beforeEach 里判断当前用户是否登录、角色是否匹配。如果没登录就跳登录页，如果没有权限就跳 403 或首页。不过真正的权限校验不能只靠前端，后端接口也必须校验用户权限。”

### 15. 对于没有特定权限的用户，前端和后端分别怎么处理？

前端处理：

- 不展示无权限入口，例如管理员后台菜单。
- 通过路由守卫拦截页面跳转。
- 显示“无权限访问”提示页。
- 引导用户返回首页或登录其他账号。

后端处理：

- 每个敏感接口都校验登录态和用户角色。
- 无权限时返回 `401` 或 `403`。
- 不把敏感数据返回给前端。

面试表达：

“前端可以通过隐藏菜单和路由守卫提升体验，但不能只依赖前端。因为用户可以直接手动输入接口地址，所以后端接口也要做权限校验。一般没登录返回 401，没有权限返回 403，前端根据状态码跳登录页或无权限页。”

### 16. 如果某次请求失败了，再次点击也会失败，你要怎么做？

这个问题要分两种情况：临时失败和稳定失败。

可以直接记这 7 步：

1. 先看错误类型，是网络失败、超时、权限失败，还是参数错误。
2. 如果是临时网络问题，可以提供“重试”按钮。
3. 如果是参数错误，不能盲目重试，要提示用户修改输入。
4. 如果是登录过期，要跳转登录或重新获取登录态。
5. 如果是后端服务异常，要给友好提示，不要让页面白屏。
6. 重试时要避免重复提交，比如按钮 loading 时禁用。
7. 连续失败时记录错误信息，方便排查后端日志或接口问题。

面试表达：

“我不会简单地让用户一直点重试。首先要判断失败原因。如果是网络波动或超时，可以提供重试；如果是 400 参数错误，说明前端传参或用户输入有问题，需要修正参数；如果是 401/403，可能是登录或权限问题；如果是 500，就要提示服务异常并记录日志。重试时还要禁用按钮，避免重复请求。”

### 17. 请求失败时前端可以做哪些用户体验兜底？

可以从这 6 点说：

1. loading 状态：让用户知道系统正在处理。
2. 错误提示：告诉用户失败原因。
3. 重试按钮：适合网络波动和超时。
4. 禁用重复点击：避免多次提交。
5. 空状态展示：接口无数据时不要白屏。
6. 降级方案：比如大模型失败时提示稍后再试，保留用户输入。

面试表达：

“请求失败时，前端要让用户知道发生了什么，而不是页面没反应。比如我会显示错误提示，保留用户输入，允许重试；如果是生成类请求，还会保留用户消息和占位气泡，避免用户觉得内容丢了。”

### 18. 后端返回的数据出错了，时间解析出现错误，怎么处理？

这个问题本质是“前端如何处理后端脏数据或格式不一致”。

可以直接记这 7 步：

1. 先在 Network 里看后端真实返回的数据。
2. 确认时间字段格式是否和约定一致。
3. 前端解析时间时加兜底，不要直接让页面报错。
4. 如果时间为空或格式错误，显示 `--` 或“时间未知”。
5. 对接口数据做格式化函数统一处理。
6. 和后端对齐时间格式，例如统一 ISO 字符串或时间戳。
7. 如果是后端数据问题，要反馈后端修复接口。

示例：

```js
function formatTime(value) {
  if (!value) return '--'

  const date = new Date(value)

  if (Number.isNaN(date.getTime())) {
    return '--'
  }

  return date.toLocaleString()
}
```

面试表达：

“如果后端返回时间格式有问题，我会先看 Network 确认原始数据。前端不能直接假设数据一定正确，所以会封装 formatTime 这种格式化函数，遇到空值或非法时间就显示 --，避免页面崩掉。同时和后端约定统一格式，比如 ISO 时间字符串或时间戳。如果是接口返回错了，也要反馈后端修正。”

### 19. 前端为什么要做数据兜底？

因为真实接口不一定永远返回理想数据，可能出现字段为空、类型不对、时间格式错误、数组为空、嵌套对象缺失等情况。如果前端不做兜底，页面可能白屏或报错。

常见兜底：

```js
const list = Array.isArray(data.list) ? data.list : []
const name = data.user?.name || '未命名用户'
const timeText = formatTime(data.created_at)
```

面试表达：

“前端要假设接口数据可能不完整，所以渲染前会做默认值和类型判断。比如列表字段不是数组时给空数组，用户名称为空时给默认文案，时间格式错误时显示 --。这样可以提升页面稳定性。”

### 20. CSS 盒子模型是什么？有哪些？

盒子模型不是 `div`。  
`div` 是 HTML 标签，盒子模型是浏览器计算元素尺寸和布局的一套规则。

一个元素可以理解成一个盒子，盒子从内到外包括：

1. `content`：内容区域，例如文字、图片。
2. `padding`：内边距，内容和边框之间的距离。
3. `border`：边框。
4. `margin`：外边距，元素和其他元素之间的距离。

可以直接记：

```text
margin -> border -> padding -> content
```

CSS 里常见两种盒子模型：

1. 标准盒模型：`box-sizing: content-box`。
2. IE 盒模型 / 怪异盒模型：`box-sizing: border-box`。

#### 标准盒模型 content-box

默认情况下，`width` 和 `height` 只表示内容区域大小，不包含 padding 和 border。

```css
.box {
  width: 100px;
  padding: 10px;
  border: 2px solid #000;
  box-sizing: content-box;
}
```

实际宽度是：

```text
100 + 10 * 2 + 2 * 2 = 124px
```

#### IE 盒模型 border-box

`width` 和 `height` 包含 content、padding 和 border。

```css
.box {
  width: 100px;
  padding: 10px;
  border: 2px solid #000;
  box-sizing: border-box;
}
```

实际占用宽度还是 `100px`，内容区域会自动变小。

#### 面试表达

“盒子模型不是某个标签，div 只是一个块级标签。盒子模型是 CSS 里描述元素尺寸的规则，一个盒子由 content、padding、border、margin 组成。常见有标准盒模型和 border-box 盒模型。标准盒模型里 width 只包含内容区，border-box 里 width 包含内容、内边距和边框。实际开发里我更常用 border-box，因为布局更好控制。”

#### 常用全局写法

```css
* {
  box-sizing: border-box;
}
```

这样设置后，元素宽高更容易计算，做响应式布局时也更稳定。

### 21. 如何实现水平居中？

水平居中要看居中的对象是什么，可以分为行内内容、块级元素、Flex、Grid、定位等方式。

#### 方法 1：文本或行内元素水平居中

```css
.parent {
  text-align: center;
}
```

适合文字、按钮、图片这类行内或行内块元素。

#### 方法 2：固定宽度块级元素水平居中

```css
.box {
  width: 300px;
  margin: 0 auto;
}
```

适合有固定宽度的块级元素。

#### 方法 3：Flex 水平居中

```css
.parent {
  display: flex;
  justify-content: center;
}
```

`justify-content: center` 表示主轴方向居中。默认主轴是水平方向。

#### 方法 4：Grid 水平居中

```css
.parent {
  display: grid;
  justify-items: center;
}
```

或者：

```css
.parent {
  display: grid;
  place-items: center;
}
```

#### 方法 5：绝对定位 + transform

```css
.box {
  position: absolute;
  left: 50%;
  transform: translateX(-50%);
}
```

适合弹窗、浮层等定位场景。

面试表达：

“水平居中要看元素类型。如果是文字，可以用 text-align: center；如果是固定宽度块元素，可以用 margin: 0 auto；如果是布局容器，我一般用 Flex 的 justify-content: center；弹窗这种定位元素也可以用 left: 50% 加 transform。”

### 22. 如何实现垂直居中？

垂直居中也要看场景。

#### 方法 1：单行文字垂直居中

```css
.button {
  height: 40px;
  line-height: 40px;
}
```

适合单行文字。

#### 方法 2：Flex 垂直居中

```css
.parent {
  display: flex;
  align-items: center;
}
```

`align-items: center` 表示交叉轴居中。默认 flex 主轴是水平，所以交叉轴就是垂直方向。

#### 方法 3：Grid 垂直居中

```css
.parent {
  display: grid;
  align-items: center;
}
```

或者水平和垂直一起居中：

```css
.parent {
  display: grid;
  place-items: center;
}
```

#### 方法 4：绝对定位 + transform

```css
.box {
  position: absolute;
  top: 50%;
  transform: translateY(-50%);
}
```

#### 方法 5：表格布局

```css
.parent {
  display: table-cell;
  vertical-align: middle;
}
```

这个方法现在用得少，但面试里可以提到。

面试表达：

“垂直居中如果是单行文字，可以用 height 等于 line-height；如果是容器布局，最常用 Flex，设置 align-items: center；如果要水平垂直都居中，可以用 Flex 的 justify-content 和 align-items，或者 Grid 的 place-items。”

### 23. 如何同时实现水平垂直居中？

#### 方法 1：Flex


#### 方法 2：Grid


### 25. 防抖和节流是什么？有什么区别？

防抖和节流都是前端性能优化手段，主要用于控制高频事件的触发次数。

常见高频事件包括：

- 输入框输入。
- 搜索联想。
- 滚动事件。
- 窗口大小变化。
- 按钮重复点击。
- 鼠标移动。

#### 防抖 debounce

防抖的意思是：事件连续触发时先不执行，等用户停止操作一段时间后再执行。

典型场景：

- 搜索框输入。
- 表单校验。
- 用户停止输入后再请求接口。

例子：

用户一直输入关键词，不应该每输入一个字就请求一次后端，而是等用户停下来 300ms 后再请求。

```js
function debounce(fn, delay = 300) {
  let timer = null

  return function (...args) {
    clearTimeout(timer)

    timer = setTimeout(() => {
      fn.apply(this, args)
    }, delay)
  }
}
```

面试表达：

“防抖适合输入框搜索这种场景。用户连续输入时不马上请求接口，而是等用户停止输入一段时间后再执行，这样可以减少无效请求。”

#### 节流 throttle

节流的意思是：事件连续触发时，固定时间内只执行一次。

典型场景：

- 页面滚动。
- 滚动加载更多。
- 窗口 resize。
- 高频点击。
- 鼠标移动。

例子：

页面滚动时事件触发非常频繁，如果每次都计算位置会影响性能，可以限制为每 300ms 执行一次。

```js
function throttle(fn, delay = 300) {
  let lastTime = 0

  return function (...args) {
    const now = Date.now()

    if (now - lastTime >= delay) {
      lastTime = now
      fn.apply(this, args)
    }
  }
}
```

面试表达：

“节流适合滚动、resize 这种持续触发的事件。它不是等用户停下来，而是限制固定时间内最多执行一次，避免函数被触发太频繁。”

#### 防抖和节流区别

可以直接记：

```text
防抖：等你停下来再执行。
节流：隔一段时间执行一次。
```

对比：

| 对比点 | 防抖 debounce | 节流 throttle |
| --- | --- | --- |
| 核心思想 | 停止触发后再执行 | 固定间隔执行 |
| 常见场景 | 搜索输入、表单校验 | 滚动、resize、拖拽 |
| 关注点 | 避免重复请求 | 降低执行频率 |

#### 项目里可以怎么联系？

面试时可以这样结合项目说：

“比如我的项目里如果有搜索候选人、搜索会话、搜索题库这种输入框，就适合用防抖，等用户停止输入后再请求后端。像聊天列表滚动、后台长列表滚动加载、窗口 resize 重新计算图表尺寸这种场景，就适合用节流。”
